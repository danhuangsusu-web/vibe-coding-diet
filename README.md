# 食刻 AI · FoodSense

用一张图片或一句话，给你的这顿饭一个看得懂、能执行的判断。

> 这是一个面向 **AI 产品经理作品集** 的微信小程序 MVP。
> 它想验证的是：把 AI 的"理解力"和规则的"确定性"分开，能不能让非标准中式外卖的饮食判断变得**可信、可解释、可执行**。
> 投入预算：约 80 小时 / 300 元。

---

## 这个项目想解决什么

传统记餐工具要求用户搜索菜品、输入克数、查营养库。但中式外卖的份量、用油、做法全都不标准——**精确热量本身就是一个假承诺**。

更现实的问题是：即便用户知道这顿饭 850 千卡，他仍然不知道**现在该怎么调整**。

| 传统做法 | 食刻 AI |
| --- | --- |
| 要求精确克数 | 只要求份量档位（小份 / 正常份 / 大份） |
| 给出单点热量 | 给出**区间**，并说明不确定性来自哪里 |
| 只有超标警告 | 给出红黄绿灯 + 1–2 条具体可执行的调整建议 |
| 纯数字呈现 | 用**灯位 + 文字 + 图标**多重编码，不依赖颜色单一传递信息 |

## 核心设计：AI 与规则的分工

这是整个项目最关键的架构决策——**AI 只负责"理解输入"，不负责"下判断"**。

| | AI 负责 | 规则负责 |
| --- | --- | --- |
| 输入 | 图片 / 菜单截图 / 文字描述 | — |
| 输出 | 菜品名、食材标签、烹饪方式、份量档位、置信度、不确定性 | — |
| 计算 | — | 热量区间、动态餐次额度、红黄绿评级 |
| 建议 | — | 从**固定白名单**中挑 1–2 条 |
| 约束 | 严格遵守结构化输出 Schema | 纯函数、确定性、可测试 |

这样换来三个好处：

1. **可解释** —— 每个评级都能追溯到具体规则，不是黑盒
2. **可复现** —— 相同输入必然得到相同输出（规则函数接收显式的 `now` 参数，不读系统时钟）
3. **可评测** —— 模型能力与规则逻辑可以分别度量，问题能归因到具体环节

### 动态餐次额度

评级不拿一顿饭和固定数值比，而是看它**相对今天还剩多少额度**：

```
当天剩余建议上限 = 每日建议上限 − 当天已摄入下限
当前餐参考额度  = 剩余建议上限 ÷ 预计剩余餐次数（向下取整）
```

| 本餐热量上限 ÷ 参考额度 | 评级 |
| --- | --- |
| ≤ 0.8 | 绿灯 |
| 0.8 ~ 1.2 | 黄灯 |
| > 1.2 | 红灯 |

两条刻意的设计：

- **时间不惩罚夜间进食**。剩余餐次数只用于分配额度，不代表"晚上吃同样的东西更差"。
- **高油高糖做法最低黄灯**。它可能不是红灯，但绝不会是绿灯。

剩余餐次数按固定时段估算（Asia/Shanghai）：

| 时段 | 剩余餐次 |
| --- | --- |
| 00:00 – 04:59 | 1 |
| 05:00 – 10:29 | 3 |
| 10:30 – 15:59 | 2 |
| 16:00 – 23:59 | 1 |

> 阈值 0.8 / 1.2 是作品集自定的产品规则，不宣称是专业营养标准。

## 用户流程

```
选图片 或 输入文字
        ↓
AI 解析为结构化菜品（含置信度与不确定性）
        ↓
用户确认、修改、增删
        ↓
规则计算：热量区间 + 红黄绿灯 + 原因 + 建议
        ↓
保存 或 暂不保存
```

**未经用户确认，不产生评级，也不写库。** 这是产品原则，不是实现细节。

## 五个页面

| 页面 | 作用 | 覆盖的关键状态 |
| --- | --- | --- |
| P01 今日首页 | 今日已记录区间、剩余额度、双入口 | 有记录 / 无记录 / 加载失败 |
| P02 餐食输入 | 拍照、相册、文字描述 | 分析中 / 权限拒绝 / 超时 / 无餐食 |
| P03 识别确认 | 增删改菜品、做法、份量 | 三档置信度（较确定 / 可能 / 不确定） |
| P04 评估结果 | 灯 + 区间 + 原因 + 建议 | 绿 / 黄 / 红、保存失败重试 |
| P05 历史与设置 | 按日期分组的记录、目标与热量范围 | 空状态、删除确认、设置折叠 |

## 技术栈

| 层 | 选型 |
| --- | --- |
| 小程序 | Taro 4 + React 18 + TypeScript（编译到微信） |
| 服务端 | Next.js 15（App Router + Route Handlers） |
| 数据库 | PostgreSQL + Prisma |
| 校验 | Zod（前后端共享同一套 Schema） |
| AI | Vercel AI SDK + OpenAI 兼容协议的单一视觉模型 |
| 包管理 | pnpm workspace（monorepo，四个工作区） |

领域计算（热量、评级、建议）全部是**纯函数**，不依赖 Next.js、Prisma 或模型客户端，因此可以独立测试。

## 项目结构

```
apps/miniprogram/     微信小程序（Taro）
apps/server/          Next.js 服务端与 API
packages/shared/      跨端 Zod Schema 与类型
packages/nutrition/   确定性营养规则（纯函数）
scripts/git-hooks/    提交前密钥拦截钩子
workflow/memory-bank/ 产品与工程文档（PRD、设计、实施计划、架构）
```

## 快速开始

**环境要求**

- Node.js ≥ 20.9
- pnpm 11
- PostgreSQL ≥ 14（或兼容的云数据库）
- 微信开发者工具
- 一个支持图片输入的 AI 模型 API Key（OpenAI 兼容协议）

**启动**

```bash
pnpm install
cp apps/server/.env.example apps/server/.env   # Windows 用 Copy-Item
# 编辑 .env，填入 DATABASE_URL 与 AI 配置；文字 AI 验收时设置 MEAL_PARSER="ai"
pnpm db:generate
pnpm db:push
pnpm db:check
pnpm dev:server
```

另开一个终端：

```bash
pnpm dev:miniprogram
```

然后用微信开发者工具导入 `apps/miniprogram`，编译输出在 `apps/miniprogram/dist`。

**常用检查**

```bash
pnpm typecheck          # 全仓类型检查
pnpm build:miniprogram  # 小程序构建
pnpm build:server       # 服务端构建
pnpm db:validate        # Prisma Schema 校验
pnpm db:check           # 数据库连通性
```

> 没有配置模型 Key 时，健康检查接口仍可运行，两条离线样例也可继续体验；普通文字解析需要完整 AI 配置并设置 `MEAL_PARSER="ai"`。图片真实解析属于步骤 21，当前仍为离线演示。

**关于密钥**：`.env` 已被 `.gitignore` 排除，且仓库装有 pre-commit 钩子，会拦截 `.env` 及疑似密钥进入提交。请勿使用 `--no-verify` 绕过。

## 边界与非目标

明确**不做**以下事情——这是 MVP 范围的一部分，不是待办清单：

- 不提供医疗诊断、营养处方或进食障碍判断
- 不采集身高、体重、BMI、疾病等敏感健康数据
- 不承诺从单张图片获得精确热量，只给区间并说明不确定性
- 不建议绝食、催吐、用药、跳餐或补偿性运动
- 不做语音输入、精确宏量营养、附近外卖推荐、全天食谱生成
- 不做正式登录、支付、社区或商业化
