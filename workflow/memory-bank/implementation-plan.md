## 执行规则

- 一次只执行一个步骤；
- 开始任何步骤前，完整阅读 `architecture.md`、`design-document.md`、`implementation-plan.md` 和 `progress.md`；
- 每个步骤只完成其列出的范围，不提前实现后续步骤；
- 每个步骤完成后先运行该步骤的验证，再交给用户验收；
- 用户明确确认后，才在 `progress.md` 记录完成并更新 `architecture.md`；
- 用户未确认时，不进入下一步骤；
- 计划只描述目标、边界和验证，不包含实现代码。

> ⚠️ D1–D5 尚待用户确认。所有受影响步骤必须先读取 `decisions.md` 和 `progress.md`；未决时不得开始相应实现，也不得自行选择方案。

## 阶段一 质量和领域基础

### 步骤 1 建立自动化测试基线

**目标**

为 shared、nutrition 和 server 配置统一的 Vitest 测试入口，并在根目录提供可一次运行的测试命令。

**范围**

- 只增加测试依赖、测试配置、脚本和最小冒烟测试；
- 测试配置必须能解析并转译 exports 指向 `src/index.ts` 的 workspace TypeScript 源码包；
- 服务端自动化测试只覆盖领域服务函数，Route Handler 保持薄封装；HTTP 行为使用人工步骤或 curl 验证，避免把 Next.js 运行时引入单元测试；
- 不修改产品行为；
- 不引入 Jest、Playwright、Cypress 或小程序端到端框架。

**验证**

- 新增的全仓测试命令执行成功；
- 冒烟测试确实被发现并运行，而不是零测试退出；
- `pnpm typecheck` 继续通过。

**验收门槛**

用户确认测试命令和输出后，才进入步骤 2。

### 步骤 2 补齐共享业务契约

**目标**

在 shared 包中定义演示资料、确认后的餐食、评估结果、餐食记录和统一 API 错误的 Zod Schema 与 TypeScript 类型。

**范围**

- 保留现有 MealItem 和 ParsedMeal 契约的兼容性；
- 明确目标方向、热量区间、评级枚举、建议 ID、必填规则版本和第 11 节列出的全部错误码及可重试标志；
- `cookingMethods` 使用受控枚举并保留 `OTHER` 与自由文本补充字段，`ingredients` 使用受控标签；
- 小程序只引用 TypeScript 类型，运行时 Zod 校验仅在服务端执行；
- 餐别、演示数据隔离和保存幂等契约分别保持 D3、D2、D4 两套候选方案，不在用户确认前选定字段；
- 不实现接口和页面。

**验证**

- 每个 Schema 至少有一个有效样例和关键无效样例测试；
- 空菜品、非法份量、非法置信度、反向热量区间和非法每日范围被拒绝；
- shared 包类型检查和测试通过。
- D2、D3、D4 已由用户确认并记录到 `decisions.md` 后，相关契约才可冻结。

**验收门槛**

用户确认契约字段与设计文档一致后，才进入步骤 3。

### 步骤 3 建立最小热量区间规则

**目标**

在 nutrition 包中建立只覆盖代表性演示和评测餐食的食材基础区间、份量调整和烹饪附加区间。

**范围**

- 先覆盖两个离线演示样例和首批代表性中式外卖；
- 规则只读取设计文档第 7.3 节的受控词表和别名映射；
- 未知食材的处理保持中性，待 D1 确认后按 `decisions.md` 实施；
- 不建设完整营养数据库，不输出精确宏量营养素。

**验证**

- 相同确认菜品重复计算得到相同区间；
- 小份、正常份和大份按预期改变区间；
- 干煸、油炸、糖醋等做法扩大或提高区间；
- 未知菜品不会得到伪精确结果；
- D1 已确认且规则行为与所选方案一致；
- nutrition 包测试和类型检查通过。

**验收门槛**

用户确认演示样例区间与不确定性表达后，才进入步骤 4。

### 步骤 4 实现动态餐次额度与评级规则

**目标**

根据资料、当天已保存记录、Asia/Shanghai 时间槽和当前餐热量上限生成动态参考额度及红黄绿灯。

**范围**

- 使用设计文档固定的剩余餐次数时间段；
- 保留现有 0.8 和 1.2 阈值含义；
- 处理零额度、超额、区间汇总和高油高糖最低黄灯；
- 评级函数显式接收 `now`，不得在领域函数内部读取系统时间；
- 服务端为唯一时间权威，按 Asia/Shanghai 计算日期和时间段；
- 时间不直接惩罚评级。

**验证**

- 0.8、刚高于 0.8、1.2、刚高于 1.2 都有边界测试；
- 每个时间段边界都有测试；
- 无历史、有历史和已超过每日范围都有测试；
- 零或负参考额度不会产生除零、Infinity 或 NaN；
- 剩余上限为 2、剩余餐次为 3 等“向下取整为 0”的情况直接判红灯且不做除法；
- 固定输入、固定记录和固定 `now` 可重复得到相同结果；
- 高油高糖餐食不会得到绿灯；
- nutrition 包测试和类型检查通过。

**验收门槛**

用户确认规则样例和边界结果后，才进入步骤 5。

### 步骤 5 实现原因和建议白名单

**目标**

由确定性规则输出主要原因、区间不确定性和一至两条白名单建议。

**范围**

- 建议只能来自 design-document.md 中批准的稳定建议 ID 与对应文案；
- 为无须调整、米饭偏多、高油、带皮和酱汁等代表情况提供规则；
- 不调用大模型润色；
- 不承诺精确减重或精确减少热量。

**验证**

- 每类代表餐食得到相关建议；
- 建议数量保持一至两条；
- 每条建议同时返回稳定 ID，展示文案与 ID 映射可测试；
- 自动扫描或断言禁止词不出现在输出中；
- 没有适用调整时返回中性“保持当前选择”；
- nutrition 包测试和类型检查通过。

**验收门槛**

用户确认文案安全性和可执行性后，才进入步骤 6。

## 阶段二 数据和 API

### 步骤 6 对齐数据库模型并初始化演示资料

**目标**

让 Prisma 模型支持已批准的目标方向和结构化建议 ID，并提供可实际执行、幂等的默认虚构 DemoProfile 初始化入口。

**范围**

- 增加目标方向；
- 增加建议 ID 存储；`advice` 继续保存当时的展示文案；
- 保留现有每日范围与 MealRecord 关系；
- 使用固定 `DEMO_PROFILE_ID`、固定虚构名称和已批准默认范围执行 upsert，接口不得按“第一条”资料定位；
- 新增 `apps/server/scripts/seed-profile.mjs`；在 `apps/server/package.json` 增加 `db:seed`，在根 `package.json` 增加同名转发脚本。`apps/server/scripts/` 只放服务端维护脚本，根 `scripts/` 保留给步骤 23 的评测脚本；
- P0 使用 `prisma db push`，不创建 migrations；执行前确认当前库无须保留的数据，或先导出；
- D2、D3、D4 对应的隔离字段、餐别字段和幂等键只在用户确认相应方案后加入；
- 不增加登录、敏感健康字段或多租户权限；
- 默认值使用设计文档批准的虚构资料。

**验证**

- Prisma Schema 校验通过；
- 按 `pnpm db:validate`、`pnpm db:generate`、`pnpm db:push`、`pnpm db:check` 的顺序完成校验、客户端生成、结构同步与连接检查；
- 初始化重复执行不会创建多个演示资料；
- `db:seed` 能从根目录执行，`GET /api/profile` 能按 `DEMO_PROFILE_ID` 读取同一资料；
- 查询结果不包含身高、体重、BMI 或疾病字段。

**验收门槛**

用户确认数据库变更和默认资料后，才进入步骤 7。

### 步骤 7 实现演示资料读取与更新接口

**目标**

提供获取和更新唯一演示资料的服务端接口。

**范围**

- 只允许更新目标方向和每日建议范围；
- 读取和更新始终使用固定 `DEMO_PROFILE_ID`，不存在时返回明确错误，不回退到数据库第一条；
- 前后端共享同一输入契约；
- 保留原值处理无效更新；
- 返回统一错误结构。

**验证**

- 默认资料可以读取；
- 合法更新后再次读取结果一致；
- 下限不小于上限、非正整数和未知字段被拒绝；
- 数据库故障返回可理解错误而不是虚假默认值；
- 接口测试、服务端类型检查和数据库检查通过。

**验收门槛**

用户确认接口行为后，才进入步骤 8。

### 步骤 8 实现餐食记录创建和查询接口

**目标**

接收用户确认菜品并由服务端重新评估后保存，获取最近记录与分日区间汇总。

**范围**

- 只接收用户确认后的结构化菜品，以及可选客户端评估快照；
- 服务端用与评估接口相同的 nutrition 规则、当前资料、当天记录和显式 `now` 重新计算热量、额度、评级、原因和建议，以服务端结果落库；
- 保存可选模型版本和必填规则版本；缺少 `ruleVersion` 时拒绝保存；
- 图片和图片路径不保存；
- 查询返回最近 30 天、最多 50 条记录；服务端按 Asia/Shanghai 分组并附每天的汇总区间，前端不二次计算；
- 客户端始终以按钮禁用和请求锁防重；是否增加 `clientRequestId` 唯一索引与服务端幂等响应待 D4 决策。

> ⚠️ 待用户确认：保存幂等见 `progress.md` 的 D4 待确认清单。

**验证**

- 合法记录保存后可查询；
- 当天热量上下限分别正确汇总；
- 不同日期的记录不计入今天；
- 篡改客户端评级、热量、原因或建议不影响最终落库结果；
- 缺少 `ruleVersion` 的写入被拒绝；
- 查询不超过 30 天和 50 条，并由服务端返回各日汇总；
- 数据库中不存在原始图片；
- 重复保存按 D4 已确认方案验证：方案 a 验证同 `clientRequestId` 返回已有记录且不新建；方案 b 验证客户端请求锁且明确记录服务端不保证幂等；
- 接口测试、类型检查和数据库检查通过。

**验收门槛**

用户确认保存字段和今日汇总后，才进入步骤 9。

### 步骤 9 实现餐食记录删除接口

**目标**

删除唯一演示资料下的指定记录，并让之后的查询反映新汇总。

**范围**

- 使用物理删除；
- 只能删除属于当前演示资料的记录；
- 不建设恢复、审计或软删除。

**验证**

- 删除存在记录后无法再次查询到；
- 当天汇总随删除更新；
- 删除不存在或不属于演示资料的编号返回未找到；
- 重复删除不会影响其他记录；
- 接口测试、类型检查和数据库检查通过。

**验收门槛**

用户确认删除行为后，才进入步骤 10。

## 阶段三 离线静态闭环

### 步骤 10 建立两个离线演示样例

**目标**

建立两个明确标记为演示数据的餐食输入、解析结果和规则期望结果。

**范围**

- 至少包含“干煸芸豆、溜肉段和米饭”组合；
- 第二个样例覆盖不同评级或不同不确定性；
- 样例使用与真实接口相同的共享契约；
- 定义统一 `parseMeal(input)` 契约：offline 实现读取本步骤样例，ai 实现调用模型；通过服务端环境配置 `MEAL_PARSER=offline|ai` 切换，不用分叉页面逻辑；
- 步骤 13 至 19 默认使用 offline；步骤 20、21 切换到 ai 时保留 offline 作为降级和演示入口；
- 样例与评测数据是否落库、是否需要隔离标记待 D2 决策；
- 不调用模型。

**验证**

- 两个样例均通过共享 Schema；
- 两个样例均可由 nutrition 规则稳定评估；
- 样例数据、区间、原因和评级内部一致；
- 样例在 P01 至 P05 的汇总、剩余额度和评级可以互相推导；
- 不沿用原型中与正式规则冲突的 1290 kcal 单点值或 650 至 850 kcal 黄灯结论；
- 样例时间避开 00:00 至 04:59；
- D2 已确认，样例保存行为与所选隔离方案一致；
- 测试和类型检查通过。

**验收门槛**

用户确认两组演示数据后，才进入步骤 11。

- 小程序构建和类型检查通过。

**验收门槛**

### 步骤 12 建立五页路由和主流程草稿状态

**验收门槛**

### 步骤 13 实现 P02 餐食输入页的离线行为

**目标**

**范围**

- 图片只在本地选择和压缩；

**验证**

- 页面只保留一个最高优先级渐变操作，失败态和键盘不会遮挡恢复入口；

## 阶段四 真实 AI 与降级

### 步骤 20 接入文字餐食解析

**目标**

实现文字输入到 ParsedMeal 的真实模型调用和结构化校验。

**范围**

- 使用现有 OpenAI 兼容供应商工厂；
- 使用共享 Schema 验证模型输出；
- 实现 `parseMeal(input)` 的 ai 适配器，并用 `MEAL_PARSER=offline|ai` 切换；offline 适配器继续作为演示和降级入口；
- Prompt 显式列出设计文档第 7.3 节受控词表，要求做法和食材只返回允许值，未命中使用 `OTHER` 加自由文本补充；
- 记录每次调用的模型版本、Prompt 版本、耗时、token 与成本；无法从供应商取得成本时记录 token，并在评测阶段按实际计费规则回填；
- 不让模型生成最终热量、评级或自由健康建议。

**验证**

- 代表性文字输入返回合法 ParsedMeal；
- 非法模型输出被拦截；
- 未配置模型时返回明确、无密钥泄漏的错误；
- 超时达到约定上限后停止等待；
- 文字解析结果只使用受控词表，未知项按 D1 已确认方案恢复；
- 离线演示入口不受影响；
- 接口测试、服务端构建和类型检查通过。

**验收门槛**

### 步骤 21 接入单张图片餐食解析

**目标**

实现小程序图片压缩、单张上传和服务端视觉模型解析。

**范围**

- 原图不写入数据库；
- 与文字输入共用 ParsedMeal Schema；
- 餐食照片和菜单截图共用解析链路，但 Prompt 按输入类型增加菜单约束：只识别用户会吃的条目，无法判断份量时扩大不确定区间；
- 不增加对象存储。

**验证**

- 餐食照片和菜单截图可以返回合法结果；
- 非图片、过大图片、模糊或无餐食图片得到明确处理；
- iOS/HEIC 输入显示可理解的转换或重新拍摄提示；
- 菜单截图不会把价格、推荐标签或整页菜品全部当作一餐；

**验收门槛**

### 步骤 22 完成真实链路错误与降级状态

**目标**

统一处理权限、网络、超时、AI 非法输出、未知菜品、数据库故障和重复操作。

**范围**

- 客户端中止时传递取消信号，服务端用 AbortController 取消模型调用并记为一次已消耗调用；供应商不支持取消时丢弃迟到结果，但仍计入评测成本；
- 失败后优先恢复到最近可操作状态；

**验证**

- parsing、assessing、saving 失败分别回到正确状态；
- 错误响应不包含密钥、连接串、堆栈或供应商原文；
- 连续点击和重复请求不会产生重复记录；
